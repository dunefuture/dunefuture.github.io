# Public participant reader — privacy compatibility audit

Status: **OPEN / REVIEW REQUIRED**. Source inspected: `championship.html` in website integration branch. No live Firestore access performed.

## Observed source behavior
- The public page initializes the Firebase client SDK with project `dune-future-championship`.
- It queries `tournaments/dune-future-championship-2027/participants` with `where("status", "==", "approved")`.
- It maps **entire document objects** using `doc.data()`, then renders only a name and an APPROVED label using DOM `textContent`.
- The separate static `championship-public.json` is a draft leaderboard with 21 empty slots. It is **not** the registration ledger.
- The new private registration flow uses `phase1Registrations`, `phase1Seats`, `phase1PersonSeats`, `phase1Roster` and related private collections. The old public reader is not a proven compatible substitute for the sanitized roster.

## Risk and limits
The `status == approved` client-side query is **not** field-level redaction. Firestore rules govern which documents can be read; the browser receives the full contents of any allowed document. Rendering only `name` does not prevent other permitted fields from being delivered to the client. Therefore this audit cannot certify the legacy participants collection as privacy-safe without examining actual deployed rules and document schemas.

## Release blockers
1. Confirm deployed Firestore rules and fields of approved participant documents without publishing personal information.
2. Decide whether the legacy public query should be removed or replaced by an explicitly sanitized public projection; preserve other tournament features.
3. Verify browser reads with anonymous, player and administrator roles against approved rules, including query compatibility and unauthorized access denial.
4. Confirm public roster is never derived from unapproved or unverified registrations.
5. Test with registration CLOSED and independent rollback approval before any public deployment.

## Current guardrail
Do not add direct browser reads of private enrollment, review, audit or identity documents. Do not change deployed rules or live collections as part of this audit. No production readiness claim.

## Confirmed source-level rules incompatibility (13 November 2026)

A cross-repository review compared the website reader with the **repository candidate rules**, not deployed production rules:

| Surface | Website client behavior | Candidate rules behavior | Finding |
| --- | --- | --- | --- |
| `tournaments/dune-future-championship-2027/participants` | Anonymous/public collection query with `status == approved` | `allow read: if !championship(tid) || isAdmin();` | **INCOMPATIBLE** for anonymous Championship readers: the candidate requires admin for this tournament. |
| `phase1Roster/{seat}` | No reader in existing public Championship page | Public `get` only when a roster document passes `publicRoster`; `list` is admin-only | A browser collection query cannot simply replace the legacy query. Any 21-seat reader must use individually authorized document gets or an approved public projection. |
| `phase1Registrations/{uid}` | No direct reader in existing public Championship page | Owner/admin `get`, admin-only `list` | **PRIVATE**; never use as a public website data source. |
| `championship-public.json` | Static public draft roster, parsed by strict allowlist | Not governed by Firestore rules | Candidate for sanitized public projection **only after** independent validation of source, approval and publication process. |

**Critical:** `development/migration/firestore.production-candidate.rules` still contains `isAdmin() = isOwner('demo-admin-only')`, which is a test-only UID. This candidate must not be deployed as-is. No statement here verifies actual deployed production rules.

### Required decision before production integration

1. Choose one approved publication architecture: static allowlisted `championship-public.json` generated by a trusted review process, or a separately designed sanitized public Firestore projection. Do **not** point the public page directly to private enrollment collections.
2. Verify actual deployed rules, admin binding and approved participant document schema in a private review, without exposing personal identifiers.
3. Implement the chosen publication path in a separate, testable change, with rollback and independent approval.
4. Keep the public Championship site and enrollment CLOSED until authorization. Green CI is insufficient.
